
# Receiver, CPU Affinity, and CPU Quota Experiments

**Project:** CPU Scheduling Covert Channel — Operating Systems Final Group Project
**Team member:** Prabha
**Evidence:** Final 15-repetition CPU-controls study conducted November 25, 2026

## 1. Objective

Evaluate receiver reliability and quantify how CPU placement and cgroup CPU bandwidth quotas affect a legitimate benchmark and the CPU scheduling covert channel.

The receiver decodes the sender's busy/idle activity by measuring its CPU execution availability. It calibrates a decoding threshold using the known `11110000` preamble before decoding an eight-bit payload.

## 2. Environment and protocol

- Ubuntu on WSL2; C programs compiled with GCC.
- CPU affinity configured with `taskset`; bandwidth restrictions with cgroup v2 via `systemd-run --user --scope`.
- Legitimate workload measured using `bin/benchmark`; competing CPU load for affinity tests generated by `stress-ng`.
- Sender/receiver payload: `10101010`; preamble: `11110000`.
- Receiver channel reliability trials: 200 ms bit duration and a shared future `CLOCK_MONOTONIC` start time.
- Fifteen repetitions **per condition**.
- CPU layout captured in the final result directory. Logical CPU labels do not, by themselves, prove a particular physical sibling/core relationship.

### Experimental design

| Component           |                                               Conditions | Repetitions |        Trials |
| ------------------- | -------------------------------------------------------: | ----------: | ------------: |
| Affinity benchmark  |                 Baseline; load on same CPU, CPU 1, CPU 2 |     15 each |            60 |
| CPU quota benchmark |                         Unrestricted, 75%, 50%, 25%, 10% |     15 each |            75 |
| Channel reliability | Same CPU; CPU 1; CPU 2; sender quotas 75%, 50%, 25%, 10% |     15 each |           105 |
| **Total**     |                                  **16 conditions** |             | **240** |

The performance benchmarks and communication tests are separate experiment sets. Benchmark slowdowns should not be presented as simultaneous measurements of a channel transmission.

## 3. CPU affinity and legitimate workload performance

The benchmark runs on logical CPU 0. In competing-load conditions, `stress-ng` generates CPU load pinned to CPU 0, 1, or 2. The names below reflect the runner's configuration labels; physical topology interpretation requires the recorded CPU topology.

| Configuration                    | Mean benchmark time | Trial-to-trial standard deviation | Slowdown vs baseline |
| -------------------------------- | ------------------: | --------------------------------: | -------------------: |
| Baseline                         |         1.599585 ms |                       0.130736 ms |              1.000× |
| Same CPU                         |         3.617696 ms |                       0.298588 ms |              2.262× |
| CPU 1 (`sibling_cpu` label)    |         1.945372 ms |                       0.165454 ms |              1.216× |
| CPU 2 (`separate_cores` label) |         1.905322 ms |                       0.120021 ms |              1.191× |

**Interpretation:** Direct contention on logical CPU 0 produced the largest slowdown, roughly 2.26× the baseline in this experiment. CPU 1 and CPU 2 load also increased mean time, but much less.

## 4. CPU quota and legitimate workload performance

The benchmark was pinned to logical CPU 0 and executed with five CPU bandwidth settings.

| CPU quota    | Mean benchmark time | Trial-to-trial standard deviation | Slowdown vs unrestricted |
| ------------ | ------------------: | --------------------------------: | -----------------------: |
| Unrestricted |         1.687714 ms |                       0.114723 ms |                  1.000× |
| 75%          |         1.768875 ms |                       0.196246 ms |                  1.048× |
| 50%          |         2.423114 ms |                       0.353554 ms |                  1.436× |
| 25%          |        11.548234 ms |                       2.973538 ms |                  6.843× |
| 10%          |        41.570623 ms |                       9.055382 ms |                 24.631× |

**Interpretation:** Quotas of 25% and 10% incurred particularly large benchmark execution-time penalties. The observed slowdown is not necessarily the reciprocal of the quota percentage; it also depends on scheduling, quota period, workload, and virtualization.

## 5. Covert-channel reliability under CPU controls

Each configuration used 15 sender-to-receiver attempts with 200 ms slots. For quota conditions, the sender received the CPU quota while sender and receiver shared logical CPU 0. The placement conditions used the CPUs specified below.

| Configuration                             | Complete decodes | Exact-message successes | Exact success rate | Mean BER on completed decodes |
| ----------------------------------------- | ---------------: | ----------------------: | -----------------: | ----------------------------: |
| Same CPU (sender 0, receiver 0)           |            15/15 |                   15/15 |               100% |                            0% |
| `sibling_cpu` (sender 1, receiver 0)    |             0/15 |                    0/15 |                 0% |                           N/A |
| `separate_cores` (sender 2, receiver 0) |             0/15 |                    0/15 |                 0% |                           N/A |
| Sender quota 75%                          |            15/15 |                   15/15 |               100% |                            0% |
| Sender quota 50%                          |            15/15 |                   15/15 |               100% |                            0% |
| Sender quota 25%                          |            15/15 |                   15/15 |               100% |                            0% |
| Sender quota 10%                          |            14/15 |                   14/15 |              93.3% |                            0% |

A **complete decode** yields an eight-bit message with successful process exits. An **exact-message success** matches the sent eight-bit payload. BER is computed only for complete decoded messages; it is **undefined**, not zero, if the receiver produces no complete payload.

**Interpretation:** Placement on different logical CPUs caused the receiver to fail to recover complete messages in this setup. Restricting the sender's CPU quota did not reliably eliminate the channel: even at 10%, 14 of 15 messages were received correctly. Strong quotas imposed a substantial legitimate-workload performance cost.

## 7. Limitations

- Results are from the final integrated WSL2 environment, not proof of universal behavior on native Linux.
- CPU affinity does not prevent other workloads from using the selected logical CPU.
- The benchmark is a synthetic computation; its slowdown may not represent every application.
- CPU quota performance is influenced by quota periods, scheduler behavior, and background load.
- The channel tests used a single eight-bit payload at 200 ms slots; other patterns/durations may behave differently.
- The labels `sibling_cpu` and `separate_cores` depend on CPU topology. Consult the captured topology rather than assuming a physical relationship from logical numbering alone.
- Fifteen repetitions per condition provide observed rates, not guarantees that rare outcomes cannot occur.

## 8. Summary

Same-logical-CPU contention increased benchmark execution time and supported reliable covert communication. Separating the sender and receiver's logical CPUs largely removed the observable signal in this implementation. CPU quotas degraded legitimate execution, sometimes severely, while leaving the covert channel functional in most tested quota configurations.
